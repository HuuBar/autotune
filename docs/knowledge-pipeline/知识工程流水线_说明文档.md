# 知识工程流水线：一份给第一次接触者的说明文档

> 本文回答四个问题：**图到底长什么样？节点里面装的是什么？前置/后置边在执行中怎么起作用？量化数字是从哪里数出来的？**
> 文中所有 YAML、日志、数字均来自仓库真实产物（github.com/HuuBar/autotune，分支 `feat/knowledge-pipeline`），每一处都标注了出处文件，可当场复算。

---

## 1. 三十秒版本

让一个 LLM agent 自动优化机器学习模型，过去是"给它任务书，让它边想边干"。问题：它会**没看数据就调参**、**把噪声当提升**、**在小验证集上搜出满分阈值就收工**——因为"先做什么、凭什么这么分支、什么叫提升"全靠模型现场发挥。

本工作把"该怎么探索"从运行时即兴，变成**执行前编排好的一张图**：

- 探索方向、假说、动作、以及它们之间的**前置依赖与互斥关系**，全部写进一个机器可读的 YAML；
- 运行时调度器只做机械操作：前置满足才解锁、每个动作做完必须验证、分支按可判条件走并记录理由；
- 执行结果写回"假说账本"，驱动下一轮重新编图。

下面用一个真实任务把这张图完整走一遍。

---

## 2. 具体例子：TBox 王者荣耀 F1 优化

**任务**：一个游戏流量分类模型，基线状态如下（来自任务书）：

| 基线事实 | 数值 |
|---|---|
| 游戏类正样本比例 | 19.5%（类别不平衡） |
| precision | 0.5042（误报 FP 主导） |
| feature_importance | 存在零重要度特征 |
| 存量代码库 | 有"声称生效但可能没接线"的机制 |
| 游戏类验证集大小 | **未知，需要侦查** |

**目标**：王者 F1 ≥ 0.75，且 Overall F1 ≥ 0.935、Recall ≥ 0.97，视频类（bilibili/抖音）F1 降幅 ≤ 0.01。

注意两个关键点：①基线线索提示了**该查什么**（接线？不平衡？特征？），但**答案在执行前是未知的**；②验证集多大是未知的——而这个数字会决定"搜阈值"这个动作可不可信。这张图必须容纳这些未知。

## 3. 图长什么样

### 3.1 整体形状

整张图（`knowledge_pipeline/fixtures/tbox_golden.yaml`）= 4 个领域、6 个假说、8 个动作、2 个决策点、10 条边。用泳道画出来：

```
L0 目标 ── 王者 F1≥0.75 ｜ Overall F1≥0.935 ｜ Recall≥0.97 ｜ 视频类降幅≤0.01（5 条机器可判断言）

D1 接线完整性    A1 接线审计 ──► ◇J1 ──"存在未接线"──► A2 修复接线
                 (recon)                                 (edit，冒烟失败→重试→通过)

D2 类别不平衡    A3 误差结构分析 ──► ◇J2 ──"FP主导且样本<500"──► A5 阈值编辑 ──► A6 全量训练 (+0.12)
                 (recon)            │                            (edit)            (run，K折协议)
                                    ┆ informs 虚线：误差结构回写 A5 的搜索范围
                                   A7 加权编辑 ──► A8 全量训练 (+0.03→复跑+0.01→uncertain)
                                    (edit)          (run)

D4 评估稳健性    A4 数据体检 ──requires──► A5、A7（先体检才准改配置）
D3 特征空间      H5 剔除零重要度特征（本轮未探索，保留到下轮）

互斥声明：A5 ⫫ A7（单原子变更）　A6 ⫫ A8（训练资源互斥）
```

图里有四种节点、四种边。下面拆开看"节点里面到底装了什么"——全部贴原文。

### 3.2 目标层节点：验收条件是"可计算的式子"，不是口号

```yaml
goal:
  statement: "王者荣耀 F1 >= 0.75，Overall F1 >= 0.935，Recall >= 0.97，视频类 F1 降幅 <= 0.01"
  acceptance:
    - "per_app.王者荣耀.F1 >= 0.75"
    - "overall.F1 >= 0.935"
    - "overall.Recall >= 0.97"
    - "per_app.bilibili.F1_delta >= -0.01"
    - "per_app.抖音.F1_delta >= -0.01"
```

每条 acceptance 都能被一个解析器（`assertions.py`）拆成 `指标路径 + 比较符 + 数值` 并对实验结果**机器求值**。后面会看到，"验收通过"这件事是调度器算出来的，不是 agent 说自己过了。

### 3.3 假说节点：一条可证伪的机制 + 一个先验 + 预期收益与成本

```yaml
- id: H1
  layer: hypothesis
  domain: D1
  title: "存在未接线的声称机制，修复接线可零成本释放收益"
  mechanism: "若机制的参数未传入，则该机制从未生效，接通后等同于无代价增加一个优化手段"
  prior: 0.5
  expected: {metric: "per_app.王者荣耀.F1", delta: "+0.0~0.3", confidence: "low"}
  cost: {recon_steps: 4, run_minutes: 5}
```

逐字段说人话：

- `mechanism`：这个假说**为什么可能成立**——没有机制的"假说"只是口号；
- `prior`：执行前对它的置信度（0.5 = 不确定），执行后会被证据更新（本例中被更新到 0.95）；
- `expected / cost`：预期收益和验证代价——调度器用**收益/成本**决定先验证谁（H2 预期 +0.05~0.20、成本 1 步侦查+5 分钟，优先级最高）；
- 假说必须有这三个东西才合法——这是校验器的硬检查，LLM 编图时漏了会被打回。

### 3.4 动作节点：做什么、用什么做、产出什么、怎么算成、允许失败几次

```yaml
- id: A5
  layer: action
  belongs_to: H2
  type: edit
  do: "实现阈值搜索（范围与步长由 error_profile 决定），改完当场解析校验配置文件"
  tool_hint: "edit_code_block"
  produces: "threshold_change"
  verify: "配置解析通过；冒烟跑通"
  retry_budget: 2
```

这是"细粒度"的真正含义：每个动作节点强制回答五个问题——

| 字段 | 回答的问题 | 没有它会怎样 |
|---|---|---|
| `type` | 这是侦查(recon)、改代码(edit)还是跑实验(run)？ | 无法区分"获取信息"和"改变状态"，回滚策略无从谈起 |
| `do` | 具体做什么 | —— |
| `produces` | 产出哪个**有名产物** | 下游没法声明"我需要它" |
| `verify` | 怎么算做成功 | agent 会说"我做完了"，但无法判定 |
| `retry_budget` | 允许失败几次 | 失败后要么无限重试，要么被静默跳过 |

### 3.5 决策点：分支条件是"读到什么就走哪条路"的显式规则

```yaml
- id: J2
  after: A3              # A3（误差结构分析）完成后触发
  read: error_profile    # 读 A3 的产物做判定
  branches:
    - if: "FP 主导 且 游戏类验证样本 >= 500"
      then: "先 A5（阈值路线）"
    - if: "FP 主导 且 游戏类验证样本 < 500"
      then: "先 A5，但 A6 的 verify 升级为 K 折或标注低置信度（H6 生效）"
    - if: "FN 主导"
      then: "先 A7（加权路线），A5 延后"
```

第 2 节留下的悬念——"验证集多大"——在这里收束：**图的形状会因为侦查结果而不同**。样本 ≥500 走普通阈值路线；<500 时图里长出一个额外约束（验收升级 K 折，即 H6 假说被激活）；FN 主导则整个改走加权路线。这就是"未知被显式编码"：不确定的分支不靠模型临场拍脑袋，而是预先写好的、可判定的条件。

## 4. 前置/后置边在执行中到底怎么起作用

这一节是核心：**每条边在执行轨迹里留下什么证据，没有它会发生什么**。轨迹原文来自一键脚本的实跑（`e2e_out/trace.jsonl`，2026-07-22）。

### 4.1 requires（硬前置）：产物没就位，动作根本不会被解锁

图里有 `{from: A4, to: A5, type: requires}`——"改配置前先体检数据"。看真实轨迹的时间顺序：

```json
{"tick": 4, "event": "execute", "node_id": "A4", "detail": {"verify_passed": true, "log": "...产出 data_health..."}}
{"tick": 5, "event": "unlock",  "node_id": "A5", "detail": {"requires": ["A4"]}}
```

**A5 的 unlock 事件只出现在 A4 通过验证之后**——调度器在 tick 1~4 里压根没把 A5 放进候选集，即使 A5 优先级更高。顺序正确性不依赖模型自觉，是图的拓扑保证的。

> 没有这条边会怎样：这正是"信息缺失型事故"的定义——先决策后补查。评测里无编排 agent 在 6 个剧本中犯了 7 起（见 §5）。

### 4.2 informs（软前置）：下游动手前，参数先被上游产物更新

```json
{"tick": 5, "event": "param_update", "node_id": "A5", "detail": {"source": "A3", "artifact": "error_profile"}}
{"tick": 5, "event": "unlock",       "node_id": "A5", ...}
```

A3 的误差结构（FP 主导、各类样本量）在 A5 解锁**之前**写入了 A5 的参数——A5 的 `do` 字段里"搜索范围由 error_profile 决定"由此兑现。防的是"用旧参数执行新动作"的脏读：没有 informs，A5 只能拿任务书里的旧数字拍一个搜索范围。

### 4.3 决策点：分支怎么走、为什么，全部落盘

```json
{"tick": 3, "event": "decision", "node_id": "J2", "detail": {
  "branch_index": 1, "condition": "FP 主导 且 游戏类验证样本 < 500",
  "reason": "FP 主导但游戏类验证样本 320 < 500，小样本搜阈值有过拟合风险 → 先 A5，但 A6 验收升级为 K 折（H6 激活）",
  "boost": ["A5", "A6"], "skip": []}}
```

三个要点：①判定**读的是产物**（error_profile 里的 320 条这个数字）；②走的是哪个分支、理由是什么**写进了日志**——不存在暗箱分支；③同一张图换一组侦查事实就走另一条路（测试里把样本数改成 600，J2 自动切到分支 0；改成 FN 主导，切到分支 2）。

### 4.4 no_parallel（互斥声明）：冲突被推迟并留痕，而不是发生后再收拾

```json
{"tick": 5, "event": "no_parallel_hold", "node_id": "A7",
 "detail": {"held_by": "A5", "reason": "单原子变更原则：同一时期只验证一个改动"}}
```

tick 5 时 A5（阈值编辑）和 A7（加权编辑）**同时满足了解锁条件**。调度器扣下 A7 并记录了原因。这不是资源不够——是**语义互斥**：若两个改动同时生效，后面的 +0.12 和 +0.03 就永远说不清是谁的贡献。同理 A6 ⫫ A8 保证两次全量训练同口径可比。

> 这条边直接回答"图编排如何避免并行冲突"：**冲突在执行前就是图里的显式声明**，调度器只需要查表。v1 用串行执行保证语义正确；这些声明是未来升级并行调度时的现成契约。

### 4.5 每个动作必验 + 失败有预算：失败不会被静默跳过

```json
{"tick": 2, "event": "verify_fail", "node_id": "A2", "detail": {"attempt": 1, "retries_left": 2}}
{"tick": 2, "event": "retry",       "node_id": "A2", "detail": {"attempt": 2, "retries_left": 1}}
{"tick": 2, "event": "execute",     "node_id": "A2", "detail": {"attempt": 2, "verify_passed": true}}
```

A2 第一次冒烟失败 → 消耗 1 次重试预算 → 第二次通过。若预算耗尽，节点进入 **blocked**（显式终态）：冻结它的下游、其他领域照常推进、终报单列"未决阻塞"交人裁决——测试里构造 A2 三次全败验证了这条完整路径。**"禁止静默跳过"是与自由 ReAct 最关键的行为差异。**

### 4.6 统计纪律：+0.03 不算是提升，除非它能复现

```json
{"tick": 8, "event": "writeback", "node_id": "H3", "detail": {"record": {
  "node_id": "H3", "status": "uncertain",
  "metrics": {"gain": 0.01, "gains": [0.03, 0.01]},
  "notes": "边际提升（实测 +0.01 < 阈值 0.05，复跑 1 次后仍未达阈），不计入战果"}}}
```

加权改动第一次跑 +0.03——在自由 agent 那里这就记为"提升"了。这里它落入了边际区间（< 0.05），触发自动复跑，复跑 +0.01 不可复现 → 假说判 **uncertain，明确标注"不计入战果"**。账本里只积累站得住的证据。

### 4.7 验收：机器核对，不听口述

```json
{"tick": 8, "event": "acceptance_check", "detail": {"final": true, "results": [
  {"assertion": "per_app.王者荣耀.F1 >= 0.75", "passed": true, "actual": 0.79},
  {"assertion": "overall.F1 >= 0.935", "passed": true, "actual": 0.937}, ...]}}
{"tick": 8, "event": "run_end", "detail": {"acceptance_passed": "5/5", "unresolved_blockers": []}}
```

## 5. 量化数据：数字从哪里数出来、该怎么读

### 5.1 实验设定（一句话版）

造了 6 个"事故剧本"（S1 断链 / S2 重复列 / S3 脆弱 JSON / S4 小样本阈值陷阱 / S5 边际提升噪声 / S6 沙箱缺依赖），让**同一个任务**被两种执行方式各跑一遍：**(a) 有编排**——按图执行；**(b) 无编排**——自由探索 agent，只有任务书。双方面对完全相同的环境事实，**唯一变量是有没有图**。指标事先登记（预登记），从执行轨迹里机械计算。实现：`knowledge_pipeline/bench/`。

### 5.2 结果总表（6 剧本聚合；逐剧本数字在评测报告里全部可查）

| 指标 | 有编排 | 无编排 | 指标的机械判定口径 |
|---|---|---|---|
| 信息缺失型事故 | **0 起** | 7 起 | 决策类事件先于其依赖的侦察产物出现 = 1 起 |
| 噪声当战果 | **0 次** | 3 次 | 把 <0.05 的提升记为胜利（claim_win/confirmed）的次数 |
| 盲抄（套用与剧本不符的卡） | **0 次** | 3 次 | 动作与剧本事实不匹配 = 1 次/张 |
| 决策点分支正确率 | **100%** | 83% | 实际分支索引 == 剧本期望分支 的比例 |
| S4 陷阱识别 | **识别** | 未识别 | 是否出现"追问样本量/升级 K 折"事件 |
| 探索方向覆盖（均值） | 2.83 | 2.17 | 至少有一个动作完成的领域数 |
| 到达验收总步数（均值） | 6.0 | 6.2 | 首个"验收全过"事件前的动作执行次数 |

读法：**前五行是主判据**——它们直接对应 §4 里每条边防住的那类失控；最后两行是参考项（见 5.4 的诚实注记）。

### 5.3 把数字还原成过程：两个剧本的完整对照

**S4 小样本阈值陷阱**（验证集只有 320 条，阈值搜索能搜出满分）。无编排侧的**完整轨迹**只有 8 个事件：

```
probe       → 看到"FP 802 / FN 121，游戏类验证样本仅 320 条"
decide      → 选阈值卡（protocol_upgrade: false —— 不追问样本量）
edit → run  → 小验证集上 val_score = 1.0（满分）
claim_win   → 宣布胜利
stop        → 3 步收工
```

它**看到了** 320 条这个事实（probe 事件里就有），但没有任何结构要求它在决策时使用它——满分面前直接收工。有编排侧走的就是 §4.3 那条路：A3 侦查 → J2 读到"320 < 500"→ 自动走"K 折验收升级"分支。**同一个事实，差别只在于：有没有一个结构逼着决策必须先经过它。** 这就是"决策分支正确率 100% vs 0%（S4 单剧本）"和"S4 陷阱识别 1.0 vs 0.0"这两行数字的全部含义。

**S5 边际提升噪声**。无编排侧：+0.03 记 claim_win、复跑 +0.01 再记一次 claim_win（噪声当战果 = 2 次），还把两张与剧本事实不符的卡直接套用（盲抄 = 2 次）。有编排侧：§4.6 的完整处理——复跑、判 uncertain、账本注明"不计入战果"。双方最终验收都只有 2/5 通过，但有编排侧**没有谎报**：终报如实写着 2/5，而无编排侧的"战果簿"里多了两个不属于它的胜利。

### 5.4 诚实注记：步数为什么没有显著差异（6.0 vs 6.2）

这是预登记指标里唯一"没赢"的一项，值得说透：无编排侧在 S4 因为**过早收工**只走了 3 步——它少走的步数正是它漏掉的工作（没追问样本量、没探索其他方向，方向覆盖只有 1）。在 S1 断链剧本里则是另一个极端：无编排侧乱试 12 步，有编排侧 7 步。**步数衡量的不是"快"，而是"有没有漏工序"**——所以我们把事故类指标作为主判据，步数只作参考。这个口径在实验前的预登记文档里已写明，不是看到结果后的找补。

### 5.5 这些数字为什么可信（评判标准的合理性）

1. **机械可复算**：每个指标都是"轨迹事件 → 计数/比率"的确定性函数（`bench/metrics.py`），有合成轨迹的精确值单测和冻结值回归——任何人拿到同一份轨迹都能算出同一个数；
2. **双方同facts**：剧本的环境事实一次注入、两侧逐字节一致，差异只在执行方式；
3. **预登记**：指标和期望在跑实验前写定，不存在"看结果定指标"；
4. **逐剧本独立计分再聚合**：防止单个剧本的运气主导结论；
5. **可重复**：确定性轨迹，同一剧本跑两遍逐事件一致——评测台本身就是整个系统的回归测试套件。
