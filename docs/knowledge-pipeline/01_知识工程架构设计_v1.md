# 知识工程架构设计 v1（执行前编排 → 执行 → 执行后验证）

> **定位**：本文档定义"知识工程流水线"的最小架构。设计纪律沿用共识文档：所有组件都从理想流程推导，不从任何现成系统照搬。
> **一句话**：把"优化"从模型即兴发挥，改造为——执行前把知识编排成一张**分层编排图**，执行时按图行走，执行后把结果写回图与知识库，使搜索可积累、可审计、可复用。

## 1. 总览：三段式流水线

```
【执行前】S1 搜集 → S2 筛选 → S3 整理（知识卡库）→ S4 编排编译（→ 编排图）
【执行中】调度器按图的语义行走：前置满足才解锁、备选分支按条件选择、
         互斥节点不可并行、每个动作带验证
【执行后】结果写回：假说后验更新 → 假说账本 → 知识库增殖 → 驱动下一批编排
```

S1~S3 已有产物（《战术知识卡 v1》，筛选规则=决策改变/动作直给/边界标注三档）。**本架构的核心新物是 S4 的"编排图"与执行语义**。知识卡是"内容"，编排图是"过程结构"（共识文档 C-02 的核心区分）。

## 2. 核心产物：分层编排图

### 2.1 四层结构（对应"领域 → 具体 skill → 具体动作"）

| 层 | 名称 | 内容 | 例子（TBox） |
|---|---|---|---|
| L0 | 目标层 | 全局目标 + 机器可判的验收断言 + 约束（不许劣化项） | 王者 F1≥0.75 且视频类降幅≤0.01 |
| L1 | 领域层 | 该任务值得探索的方向域，互相正交 | 接线完整性 / 类别不平衡 / 特征空间 / 评估稳健性 |
| L2 | 假说层 | 领域内候选假说，带机制解释、先验置信度、预期收益、验证成本 | "存在未接线机制，修复可零成本释放收益"，prior 0.5 |
| L3 | 动作层 | 原子可执行步骤，绑定工具提示，带产物与成功判据 | "追 train 入口→fit 的调用链"，产出 wiring_report |

### 2.2 边（前后置与并行约束）

| 边类型 | 语义 | 例子 |
|---|---|---|
| `requires` | 硬前置：B 需要 A 的产物的才能解锁 | 修复接线 requires 接线审计报告 |
| `informs` | 软前置：A 的产物影响 B 的参数/分支 | 误差结构分析 informs 武器选择 |
| `alternatives` | 二选一/多选一（互斥分支），附选择条件 | 阈值上调 vs 正类加权 |
| `no_parallel` | 不可并行（资源互斥或语义冲突） | 两次全量训练互斥；改同一文件互斥 |

### 2.3 节点状态机

`pending → ready（前置全满足）→ running → confirmed / refuted / blocked（重试预算耗尽）`
blocked 节点升级处理：回报 + 由编排器决定是否改道，**不允许静默跳过**。

### 2.4 决策点（decision node）

特殊节点：在某个动作完成后，读取其产物，按**可判定条件**选择下游分支。条件尽量确定性（如"报告中存在未接线机制"），必须由模型判断时，判断理由强制落盘。

## 3. 执行前流水线（怎么得到图）

```
S4 编排编译器（compiler）：
  输入：知识卡库 × 任务书 × 内部地形侦查结果
  输出：编排图（YAML/JSON，符合 schema）
  职责：① 从卡库选相关卡并给出适配论证（不用之卡给出拒绝理由）
       ② 把卡的方法论实例化为 L1~L3 节点与边
       ③ 标注每个假说的先验与验证成本（依据卡中经验反馈+地形事实）
       ④ 自检：每个动作有验证判据、每个假说有机制解释
  硬性校验（schema validator，确定性）：DAG 无环、所有 requires 指向存在节点、
       每个 action 有 verify、alternatives 组完整、验收断言可解析
```

编译器由 LLM 担任，但**产出必须通过确定性校验才可执行**——模型的创造性被约束在 schema 内，这是防止"即兴发挥"的关键设计。

## 4. 执行语义（调度器规则）

- E1 解锁：节点的全部 `requires` 前置已 confirmed 且产物就位 → ready；
- E2 选序：多个 ready 节点时，默认按编译器标注的优先级（= 预期收益/验证成本），可被策略覆盖；
- E3 备选分支：到决策点，读产物评估条件，走对应分支，条件判定结果与理由落盘；
- E4 不可并行：`no_parallel` 节点永不同时调度（v1 串行执行，该约束是面向未来的声明）；
- E5 每动作必验：verify 失败 → 重试（retry_budget）→ blocked → 升级，禁止静默跳过；
- E6 参数回写：`informs` 源节点完成后，目标节点参数先按产物更新再解锁；
- E7 早停：连续 k 个假说验证无验收进展 → 停止并报告（k 默认 3，防单轮噪声触发）；
- E8 写回前置：节点写回完成前，不得解锁下游。

## 5. 执行后：回写与增殖

1. **假说账本**（hypotheses.jsonl，append-only）：每个假说一条 `{id, 机制, 先验, 结果 confirmed/refuted, 实测收益, 证据路径, 后验置信度, 时间}`——指标是数据不是文本；
2. **领域复盘**：按领域聚合收益，更新领域先验（哪些方向值得继续投）；
3. **知识库增殖**：本轮新经验（有效的方法、踩过的坑）提炼成新卡或既有卡的"边界"补充，**必须带来源与是否已验证的标记**（防记忆回授污染）；
4. **下一批编排**：以更新后的先验 + 账本为输入，重跑 S4——图是活的，每轮重生而非维护一份死文档。

## 6. 与 autotune 的关系

本架构是**前端**（知识→图→调度），autotune 是**执行后端**（沙箱、工具、git 纪律）。两者间只有一个薄适配层：调度器把 L3 动作翻译成 autotune 的任务/工具调用，把产物/指标翻译回图。**不要求改造 autotune 核心**——W3 的工程修复（核验门禁、JSON 校验等）照常进行，互不阻塞。

## 7. 环境无关的开发验证策略（重要）

为规避对 TBox/dsv4/Docker 的依赖，开发与测试分两级：
- **L1 离线级（本阶段主力）**：schema 校验器、编译器（离线 LLM 调用）、**dry-run 调度模拟器**（mock 执行器返回预制产物，输出完整执行轨迹日志）、账本——全部可用单元测试 + 黄金夹具（`02_示例编排图_tbox.yaml`）验证；
- **L2 接入级（环境打通后）**：适配层接真实 autotune，先跑 dry 任务（如只侦查不训练）再上真任务。

## 8. 非目标（本版不做）

不做自动假说分叉的树搜索调度（等假说质量压测数据）；不做自动技能发现；不改模型与温度；不做多 GPU 并行执行。这些是有意延后，不是遗漏。
